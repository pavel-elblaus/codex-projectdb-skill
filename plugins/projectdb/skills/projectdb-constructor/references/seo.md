# Техническое SEO и приёмка ProjectDB

Использовать при разборе SEO-ТЗ, проверке шаблонов и подготовке переноса на ProjectDB. Условия конкретного сайта, включая правила URL, языки, цели производительности и ограничения публикации, брать из проекта.

## Контекст и результат проверки

- Определить источник страниц, используемую сборку ProjectDB, домены, языки и статус индексации. Для приёмки различать локальный или опубликованный прототип, целевую сборку ProjectDB и действующий сайт.
- Для каждого требования ТЗ записать фактическое состояние, доказательство, оставшееся действие и этап проверки. Связать его с существующей задачей, если она уже есть. Чужие домены, настройки и плагины из примеров оценивать по применимости.
- Сверять отдельно исходный HTML, поведение DOM после выполнения JavaScript и HTTP GET со статусом, заголовками и телом ответа. Указывать, в какой среде получено доказательство. Статический экспорт подтверждает только то, что в нём проверено. Для невыполненной части фиксировать зависимость и критерий приёмки.
- Вносить исправления там, где задаются настройки страницы, данные или общий Twig-модуль. Проверять все затронутые варианты. Для новой служебной страницы сначала проверить штатный компонент. При изменении семантики сравнить видимый текст, вёрстку и интерактивность на согласованных экранах.

## Страницы и шаблоны

- Проверить основной заголовок, иерархию заголовков, title и description. Важное содержимое выводить в начальном HTML. Для навигации использовать `<a href>` с понятным названием. Ссылке из одного изображения дать содержательный `alt`, ссылке из одной иконки — доступное имя. Для форм и меню проверять и исходную разметку, и фактическое поведение на ПК и телефоне.
- Проверить, что близкие страницы решают самостоятельные задачи. Опираться на полезное фактическое содержание и согласованные данные. Один H1 может быть правилом проекта. Процент уникальности и Text Ratio не использовать как меру качества, технические данные сохранять точными.
- Использовать [контракт метаданных, языков и маршрутов ProjectDB](projectdb-rules.md#10-карта-сборки-project-mapjson). Проверять системный head в ответе. Отдельные поля микроразметки, canonical и прочие системные значения не добавлять во входящую ветку `meta`.
- Для эквивалентных адресов выбрать один основной URL и согласовать его с внутренними ссылками, canonical и XML sitemap. Адреса реальных страниц пагинации ведут на собственную выборку через доступные GET-ссылки. Проверять их собственный canonical. Для сортировки, фильтров и отслеживающих параметров определить, меняется ли содержимое и какой адрес должен индексироваться.
- Связывать через `hreflang` эквивалентные страницы разных языков. Проверить допустимые коды, абсолютные адреса, ссылки на себя и обратные связи. Сверить с языковой веткой, переключателем и canonical. Для отсутствующих переводов не подставлять главную другого языка. В изученной версии `head.twig` цикл `response.link` выводит `rel` и `href` без атрибута `hreflang`. Если его добавляет адаптер прототипа, при переносе отдельно подтвердить источник и итоговые языковые ссылки в серверном `<head>`.
- Для навигации использовать [штатную HTML-карту ProjectDB](base-components.md#html-карта-сайта) и проверять её по актуальному дереву. В XML sitemap проверять абсолютные канонические URL, доступные для индексации, без служебных окон, ошибок и дублей. Если есть `lastmod`, сверять его с содержательным изменением страницы. Проверять ресурсы, ссылки и якоря, включая варианты пагинации.

## Серверная приёмка

- Запросить обычные страницы и характерные варианты. Проверить первую, следующую, последнюю и некорректную страницы пагинации. Для корректных адресов подтвердить HTTP 200, выборку, HTML и метаданные до выполнения JS. Для неизвестного пути проверить HTTP 404 и навигацию со страницы ошибки. Для намеренно удалённого ресурса допустим 410, при серверном сбое — подходящий 5xx. Проверка одного успешного ответа не выявляет soft 404, цепочки и циклы.
- Проверить выбранное зеркало, HTTPS и сертификаты, итоговые ответы вариантов протокола, хоста, регистра и слеша. Согласованные постоянные переходы должны сохранять путь и значимые параметры там, где они влияют на назначение. Внутренние ссылки направлять на действующие конечные адреса. Нормализацию ограничить нужными URL, сохраняя регистр ресурсов и значения параметров.
- Проверить фактический `robots.txt` для нужных хостов и протоколов, директивы для нужных роботов, доступ к необходимым ресурсам и адрес XML sitemap при наличии карты. `Disallow` управляет обходом. Для исключения через `noindex` робот должен прочитать метатег или заголовок `X-Robots-Tag`. Для закрытых материалов применять контроль доступа. Сверять правила тестовой и рабочей среды отдельно.
- После подключения штатных данных проверить кеш и системные функции. Отправку форм, доставку, скачивание файлов и интеграции проверять по согласованному сценарию на целевой сборке. Готовый интерфейс сам по себе не подтверждает обработку на сервере.
- Для производительности записывать устройство, сеть, шаблон, состояние кеша и происхождение данных. Полевые LCP, INP и CLS оценивать по реальным посещениям, на 75-м перцентиле отдельно по мобильным и настольным устройствам. Lighthouse подходит для лабораторной диагностики. TBT не заменяет полевой INP. Применять актуальные пороги и отдельно фиксировать цели проекта.

## Перенос действующего сайта

1. До переключения сохранять доступность и режим индексации действующего сайта. Зафиксировать прежние URL, статусы, метаданные, языки и sitemap. При наличии данных учесть трафик, внешние ссылки и исходную индексацию.
2. Сохранять действующие полезные URL, где возможно. Для изменяемых путей составить соответствия между прежними и релевантными новыми. Для каждого спорного соответствия фиксировать прежний HTTP-статус и основание эквивалентности, например назначение услуги или точную модель. Неоднозначные случаи и подтверждённые алиасы отмечать отдельно. По согласованной карте настроить и проверить постоянные серверные редиректы. Срок их действия согласовать с учётом рекомендаций поисковых систем. Массовый переход неизвестных URL на главную не выполнять.
3. Согласовать момент запуска и возможность отката. На рабочем домене повторить серверную приёмку, проверить, что тестовые ограничения индексации сняты. При наличии доступа подать актуальную XML sitemap. Инструмент смены адреса рассматривать только при смене домена или поддомена, если переход поддерживается.
4. После запуска наблюдать за обходом, индексацией, трафиком и полевыми CWV. Для доступности проверять появление 5xx, срок сертификатов и доставку уведомлений ответственным. Мониторинг пользовательских сигналов и доступности продолжать после разовой приёмки.

При уточнении требований сверять официальные материалы Google Search Central по `noindex`, canonical, пагинации, локализованным версиям, sitemap и переездам, справку Яндекс Вебмастера по `robots.txt` и статью web.dev «How the Core Web Vitals metrics thresholds were defined».
