**Модульный JavaScript и загрузка ProjectDB**

- `app.js` из `base/upload/system/` — отдельная общая системная библиотека-загрузчик/инитер. `jquery.pdbw.js` — набор базовых библиотек, который подключается базовым шаблоном. В исходных конфигурациях сначала идёт массив `base_javascript`, затем `javascript`, с сохранением порядка элементов. При создании кеша ProjectDB объединяет и сжимает эти ресурсы в один `ruscript.js` для русской версии; это не основание объединять модульные исходники вручную. `app.js` остаётся отдельно и запускает штатную загрузку/инициализацию. Схема CSS и проверки кеша описана в разделе «Сборка ресурсов для публикации» файла [projectdb-rules.md](projectdb-rules.md).
- Прежде чем писать индивидуальный скрипт, проверить штатные инструменты ProjectDB, возможности CSS и уже подключённые библиотеки по примерам владельца. Не повторять собственным кодом возможности доступного инструмента; сохранять текущий вид, настройки и функции.
- Системные объекты `PDBW` принадлежат загрузчику. В изученном `app.js` свойство `PDBW.variable` объявлено `writable:false`, `configurable:false`; значения читаются через `get(name)` и передаются через `set({имя: значение})`. Не заменять этот объект и не применять `Object.assign(PDBW, {...})` к системным свойствам: ошибка может появиться только после подключения настоящего `app.js`. Прототипный адаптер сохраняет существующий API и добавляет только отсутствующие части своего окружения; его проверки должны загружать реальный загрузчик и кеш вместе.
- Собственный JS секции хранить в `module/<группа>/javascript/<имя>.js` и подключать в соседнем `<имя>.twig.json`. В общей оболочке оставлять только общее поведение. Повторяемые механизмы выносить в небольшие общие функции, а не в скрипт с поведением всех модулей.
- `PDBW.module` к моменту загрузки собственного JS гарантированно существует; проверки его наличия не добавлять. Ожидание конкретного модуля через `PDBW.module.get(name, callback, true)` — другая задача и допустимо, если порядок регистрации этого модуля заранее не известен.
- Для обычного модуля использовать `!function ($, window, document, name){ ... }(window.jQuery, window, document, "группа.имя.twig");` и регистрацию через `PDBW.module.set`. Объявлять только необходимые методы: `onload` для фактического запуска поведения/плагина, прикладной `update` для обработки новых данных. Если нужны лишь события, использовать пустой объект методов и однократный третий callback.
- Загрузчик загружает JS один раз. Не добавлять защиту «повторная загрузка безопасна», собственную повторную регистрацию, window.* mount/release-менеджер или функции очистки в jQuery.data/DOM-атрибутах. Третий callback set выполняется один раз: локальное состояние и делегированные события размещать здесь. Возвращённый объект доступен методам как `this.local`.
- Повторный onload после очереди ресурсов — не повторная регистрация файла. Подключать виджеты к новым элементам, не пересоздавая события или глобальные наблюдатели. Наличие экземпляра проверять штатными средствами плагина. Состояние хранить в замыкании либо его экземпляре, без дополнительных window-контроллеров и служебных функций в data модуля. Атрибуты содержимого и UI-состояния (id/for, class, hidden) использовать по назначению.
- `onload(event, config)` вызывается загрузчиком после завершения очереди JS, включая повторную подгрузку. В нём подключаются виджеты к готовой разметке. Однократные события регистрировать в третьем callback set, а не пересоздавать при onload.
- Наличие `update($module, data, callback)` перехватывает штатное обновление: загрузчик вызывает этот метод вместо дополнительного запроса HTML. Пустой update, один callback или повторный init готовой разметки блокируют обновление содержимого. Если HTML формирует Twig и клиентская обработка новых data не нужна, не объявлять update: ProjectDB запросит обновлённый HTML штатно. При действительном клиентском update обрабатывать новые согласованные данные текущего экземпляра и завершать callback один раз; инициализацию виджетов готового HTML оставлять в onload.
- Обычным модулям не добавлять системный `destroy`. Такой контракт использовался для include form2; не распространять его на другие компоненты по аналогии. Однократные делегированные обработчики не пересоздавать. Ресурсы виджета освобождать при фактическом удалении его DOM.
- `PDBW.module.set` не дополняет и не перезаписывает зарегистрированный модуль. Дополнение form2 подключать отдельным файлом к базовому шаблону. Для оформления использовать существующую DOM-разметку, делегированные события ввода/reset, штатные события обновления include (например form2.text.twig.update) и обработку фактической вставки полей. Не перезаписывать методы form2, его Twig, include, data, отправку или штатную очистку. Начальный запуск оформления выполнять из onload общей оболочки.
- `create(data)` — вспомогательная функция, а не обязательный метод модуля. Обычно используется include по образцу базы; добавлять её только при реальном потребителе API. Не требовать от include копирования жизненного цикла стандартного модуля.
- Если Twig уже выводит готовую разметку, не повторять её сборку в JS и не добавлять зависимый `update` без фактического вызова. Для include, обслуживающего только действия пользователя, достаточно однократного callback `PDBW.module.set(name, {}, function () { ... })`; пустые onload/update и ожидание неиспользуемого JS-модуля не нужны. Существующий востребованный API include сохранять.
- Системный `onload` не включать в список вызываемых пользовательских функций `.js.json`; описывать `update` и необходимые прикладные функции. Не запускать обычный модуль самостоятельно в конце JS-файла.
- В соседнем `.js.json` использовать стандартные `function` и при необходимости `variable`; `function.update` описывается массивом с одним образцом входящего data. Не добавлять искусственные поля ради документации. При `create` описать его реальный вход. Поле `!` поясняет ограничения функции. Схему сверять с `.twig.json` и установленной базой.
- Комментарии: короткие русские `//` перед функцией, событием или значимым действием. Имена, jQuery-приёмы и оформление сверять с предоставленными проектами владельца. Библиотечные оригиналы не переписывать.


Пример status.js использует поля title и count, которые должны быть объявлены и в конфигурации Twig соответствующего модуля. Twig выводит исходный статус сразу, поэтому onload не объявлен; update показан только для действительно требуемого клиентского изменения статуса. В update проверяется data == null; нулевое количество сохраняется. Пример form2-theme.js показывает дополнение через события include без изменения методов формы. jQuery-плагин содержит проектное оформление и вызывается из onload оболочки; это схема подключения, а не готовая реализация оформления.

Источники проверенной модели загрузки: base/upload/system/app.js и base/javascript/jquery.pdbw.js; формат JS/JSON сверялся с block/nearest-webinar и block/notifications проекта владельца. set регистрирует имя один раз; get(..., true) ждёт конкретную регистрацию, не наличие PDBW.module. onload повторяется для всех зарегистрированных модулей после очередной загрузки ресурсов.

Пакет form2: index.twig строит сетку по includes/grid и помещает код данных полей в форму. jquery.includes.js сохраняет согласованные данные у [module] и предоставляет get/set/del. module.index.js инициализирует поля через local.module_exec(..., "init"); update сравнивает полные данные переданных существующих полей, использует create при смене типа, update при том же типе и серверную перезагрузку при отсутствии подходящего метода. Очередь обновлений и callback принадлежат базе. module_exec(..., "destroy") относится к управлению include. Ввод/submit проходит save_change и update_form_data с серверными событиями; тема не должна дублировать эту обработку. Наличие служебного метода в конкретной поставке не означает общего протокола destroy для обычных модулей.


**Собственное поведение, события и CSS**

- Начальное отображение, адаптивный порядок, размеры и положение элементов, закрытое состояние меню и панелей задавать Twig/CSS. Не добавлять классы ready/init скриптом только ради возможности показать уже готовый HTML. Это не относится к служебным классам и фактической инициализации внешнего плагина.
- Не вычислять повторно язык HTML, текущий адрес или производные подписи по URL, если они уже корректно выведены системой/Twig. Само наличие hashchange/popstate не означает, что сайт использует клиентскую маршрутизацию; такие слушатели добавлять только для реального сценария обновления без перехода страницы.
- Если задача сводится к действию пользователя, регистрировать ограниченный владельцем делегированный обработчик один раз. Не запускать общую функцию вроде pageScroll из onload каждого модуля ради навески одинаковых слушателей. Общий механизм оправдан фактическим повторением; специфические действия остаются у владельцев.
- В изученном `form2.radio-list.twig` radio изначально выводятся без HTML `name`. База обрабатывает выбор в пределах поля и сериализует его через `data-name`. Когда нужна нативная группа, задавать общий HTML `name` только для вариантов одного экземпляра поля, уникальные `id` и связанные `label[for]`. Перепривязывать после замены полей и проверять два экземпляра, клавиатуру, обязательность и reset.
- Зависимые поля нескольких форм пересчитывать в пределах формы изменённого input/checkbox/radio; при первоначальном onload обработать все экземпляры. После native reset значения восстанавливаются после события: отложенный пересчёт выполняется для этой формы, без повторного обхода всех форм страницы. Сохранять required/disabled, штатные события include и исходную валидацию. В изученном form2 проверки обязательности и сбор значений работают отдельно. Getter текстового поля может вернуть сохранённое значение скрытого или disabled-поля. Для условных данных проверять сценарий «заполнил → сменил вариант → отправил» и обрабатывать только применимые поля по серверному условию. Нужно ли сохранять ввод при возврате к варианту, определяет сценарий формы.
- При настройке анимации окна учитывать обработчики завершения базового плагина. В изученном dynamic-box событие `transitionend` непосредственно от `.dynamic-box-html` вызывает его `hide().show()` при открытом окне. Дополнительный transition на этой оболочке способен конфликтовать с её перерисовкой. Сверить версию и фактическую причину; если проекту нужна собственная анимация оболочки, выбирать совместимый механизм, не переписывая базовый обработчик.
- Проверять, решаются ли визуальные перемещения и анимация стилями, прежде чем измерять координаты, переносить DOM или править inline-стили в JS. Дополнения к библиотечному resize/наблюдатели добавлять только для воспроизведённой проблемы, которую штатный API не закрывает, и проверять на соответствующем переходе размеров.
- Для воспроизведённой проблемы с частыми resize проверять, не выполняется ли один и тот же расчёт несколько раз за кадр. Если нужна дополнительная отложенная обработка, хранить один ожидающий requestAnimationFrame и отменять предыдущий; не накапливать очередь init/refresh. Это не основание добавлять свой resize-слой поверх работающего плагина.
- Если `MutationObserver` действительно необходим, обрабатывать затронутые добавленные/удалённые узлы в пределах владельца. Изменение счётчика или текста слайда не должно запускать повторный обход всей страницы и пересоздание виджетов. Предпочитать штатный lifecycle/события плагина, когда они закрывают задачу; наблюдатель не является обязательным дополнением к модулю.
- Для необязательного внешнего виджета предусмотреть содержимое, доступное до загрузки API и при его недоступности, например адрес и ссылку на карту. При асинхронной загрузке совместимые экземпляры могут делить запрос API. Перед инициализацией проверить, что экземпляр ещё в DOM, при удалении освободить только его ресурсы.

**Один инициализатор, разные слайдеры**

- Сначала сохранить ресурсную группу плагина и наследование её базовых библиотек. Пример владельца: собственные Twig в `module/owlcarousel2/template/` и общий `owl.carousel.init.js` в этой же группе; библиотека `owl.carousel.min.js` и её `owl.carousel.css` наследуются из `base/module/owlcarousel2`, а не копируются в бизнес-секции. Повторное использование JS не требует переноса библиотеки в `sections`.

- Каждое Twig-представление перебирает структурированные данные своей ленты. Обобщать инициализацию плагина, а не превращать все ленты в data.html|raw. Не добавлять JS create/update, пересобирающие готовый HTML из строки, ради общей оболочки слайдера.
- Несколько .twig.json могут подключать одни и те же существующие файлы библиотеки и общего инициализатора. Их однократную загрузку обеспечивает ProjectDB; порядок библиотеки и адаптера сохранять. Не дублировать общий файл по экземплярам и не подключать его фиктивным include.
- Общему скрипту достаточно найти готовые контейнеры, прочитать согласованный config, привести числовые значения по примерам владельца и вызвать API плагина. Для реальной связи с макетом допустимы внешние стрелки, счётчик и синхронизация превью. Содержимое, ссылки и изображения отрисовывает Twig.
- Если библиотеке нужен запуск и после динамической подгрузки, использовать штатный вызов onload загрузчиком, проверяя уже созданный экземпляр средствами плагина. Документировать общий ресурс как инициализатор; не придумывать ему входной HTML или самостоятельный Twig-модуль только ради регистрации. Обработчики и наблюдатели остаются в однократном callback регистрации.
- Тип карусели, loop/autoplay, брейкпоинты и необходимость самого плагина определять по заданию и макету текущего проекта. Не превращать решение одного сайта в правило «все списки — OwlCarousel».

**Карусели: способы ввода и проверка состояния**

- Сначала сверить возможности установленной версии и конфигурацию. Не заменять собственными циклами библиотечные autoplay, resize, mouseDrag и touchDrag. Дописывать только связь с макетом, которую не даёт штатный API: внешние стрелки, счётчик, синхронизацию превью.
- Перетаскивание мышью с зажатой кнопкой, свайп пальцем и двухпальцевая прокрутка тачпада (`wheel`) — разные сценарии. У штатного OwlCarousel 2.3.4 есть mouseDrag/touchDrag; поддержки wheel одной настройкой нет. Не добавлять wheel-адаптер автоматически под видом исправления свайпа. Если требуется дополнительное поведение, обозначить ограничение и согласовать расширение; если владелец выбрал штатное поведение — оставить без дополнений.
- Проверять реальное переключение в обе стороны, а не только значения опций. Указывать испытанный ввод: имитация mouse drag не подтверждает физический тачпад или телефон. Если элементы помещаются в один кадр, отсутствие перемещения само по себе не ошибка.
- Геометрию до запуска плагина задаёт CSS по пропорциям макета/изображений, например intrinsic width/height и aspect-ratio. Не лечить скачок при F5 таймером, задержкой показа или принудительной прокруткой. Проверять размеры до/после инициализации, загрузку изображений/шрифтов и восстановление scroll position: стабильная карусель не исключает другой причины сдвига.
- Проверять крайний слайд на узком экране → расширение → сужение обратно: не должно быть пустых позиций, устаревшего индекса или рассинхронизации главного фото, активного превью и счётчика. Число видимых превью и поведение последнего/+N задаёт текущий макет; выбор кадра и открытие галереи проверять отдельно после resize и drag. Не вводить собственный пересчёт, пока не проверены штатное обновление плагина и CSS.
